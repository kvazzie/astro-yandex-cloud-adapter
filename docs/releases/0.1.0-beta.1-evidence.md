# First beta publication evidence

This record belongs to [issue #17][publication]. It does not complete or close
the [parent specification][spec]. As observed on 2026-10-07, the public npm
registry returns HTTP 404 for `@astro-yandex-cloud/adapter`. Nothing has been
published. The prerequisite implementation and release PR stack is still open.

## Release blockers

The [accepted #63 decision][decision] and [parent amendment][amendment] supersede
the original Manifest and direct-invocation requirements before first publication.
The draft Manifest contract in [#7][manifest] must be implemented, and
[#67][gateway], [#68][not-found], [#69][direct], and [#70][partition] remain open.
Do not freeze the draft Manifest v1 or publish this candidate until their
requirements are implemented and verified, or the maintainer explicitly revises
the release scope in the specification.

The final candidate must accept Function Artifacts without Sharp or runtime image
transformation support claims. PR #80 removes the regression that made those
claims mandatory. Land that fix and verify the accepted shape with the final
tarball's parser, JSON Schema and TypeScript declarations before publication.

The package is still the unpublished `0.1.0-beta.0` seed. Version preparation and
its reviewed Changesets PR must produce `0.1.0-beta.1` on protected `main`.
Neither this evidence file nor a passing rehearsal is publication evidence.

## Publication and registry result

Complete the [protected publication procedure](../beta-releases.md). Retain the
run URL, environment approval, source SHA, `publication-candidate` artifact and
its `package-check.json`. The `registry-verification` job runs independently of
the protected job, with read-only GitHub permissions and no npm publication token
or OIDC access.
It downloads the registry archive, compares it to the publication SHA-512, then
installs the exact version from npm in a clean application. The checker verifies
the installed integrity and npm provenance attestations, builds both Targets,
validates the Manifest, invokes generated handlers, and runs both previews.

If publication used the earlier workflow or registry verification failed after
npm accepted the version, download the original `publication-candidate` report
and run the same check from this checkout:

```sh
pnpm release:verify --candidate-report /absolute/path/to/package-check.json --source-commit <approved-publication-SHA>
```

Use the original publication run's full 40-character source SHA, not a later
checkout HEAD. The verified provenance must name this repository, `release.yml`
on `main`, and that commit.

Retain `.artifacts/registry-check.json`. A failure removes stale success evidence.
Never substitute a newly packed report for the publication report. Rerunning an
already published version does not recreate its original candidate evidence;
the workflow skips automatic verification and points to this recovery procedure.

- [ ] Publication run, exact source SHA and approving human recorded.
- [ ] Registry version is `0.1.0-beta.1`; `beta` selects it and `latest` does not.
- [ ] Registry bytes match the approved candidate, and npm verifies its provenance.
- [ ] Registry-installed application builds, handler, Manifest and both previews pass.
- [ ] Published GitHub prerelease URL and exact tag/source SHA recorded. Remove the
      preparation paragraphs from the release notes only after evidence passes.
