# `0.1.0-beta.1`

These are candidate release notes. Publication is pending. Review them against
the final candidate and remove this paragraph only after the release evidence
is complete.

`@astro-yandex-cloud/adapter` is a beta Bare Adapter for Astro `^7.1.0` on
Node.js `>=22.12.0`. Cloud Functions compatibility has not been verified in real
Yandex Cloud. Sharp and runtime image transformation remain experimental with
the `install` dependency strategy and unsupported with `bundle`.

After verified publication, install the beta in an Astro application:

```sh
npm install --save-exact @astro-yandex-cloud/adapter@beta
```

The first beta uses version `0.1.0-beta.1` and the `beta` dist-tag. It is not a
stable `latest` release. Commit your application's lockfile.

## Locally verified behavior

- The Object Storage Target generates a Client Artifact for Static-only Builds
  and rejects executable On-demand Routes.
- The Object Storage + Cloud Functions Target generates a Client Artifact and,
  when required, a Function Artifact. Route discovery includes Astro-internal
  and integration-injected routes. Actions execute through API Gateway payload
  `0.1` in the local generated-handler checks.
- Generated handlers preserve the locally tested request paths, query values,
  headers, text and binary bodies, cookies, redirects, errors, middleware, and
  invocation context. Origins use Host over HTTPS, with Astro `site` as fallback.
- `astro preview` serves Static-only Builds and Runtime Builds from an installed
  adapter package, including non-root base paths, assets, Actions, and endpoints.
- The packaged Deployment Manifest parser and JSON Schema validate the actual
  Serving Artifacts, route references, and Object Storage placement. Unknown
  schema versions fail; additive version 1 fields are tolerated. Function
  Artifacts omit support claims, following
  [#63](https://github.com/kvazzie/astro-yandex-cloud-adapter/issues/63). Sharp's
  experimental status remains in documentation and verification.
- `bundle` includes ordinary JavaScript dependencies using Astro's pipeline.
  `install` emits exact runtime dependency metadata and a deterministic lockfile.
  Unsupported dependencies fail the build. Builds report local artifact sizes.

Deployment, Request Routing, and Provisioning remain user-owned. The adapter
does not allocate cloud resources or upload artifacts.

## Evidence limits and pending routing work

Local builds, generated-handler tests, clean-package checks, previews, and local
S3 tests do not prove Yandex Cloud compatibility. Object Storage website
semantics, actual Cloud Functions invocation limits, and native Sharp execution
need real-cloud evidence before stable promotion.

The current candidate still lacks the Gateway template, recursive Object Storage
404 behavior, validated direct Function URL restoration and forms, and configured
Function partitioning agreed before publication. These are tracked in
[#67](https://github.com/kvazzie/astro-yandex-cloud-adapter/issues/67),
[#68](https://github.com/kvazzie/astro-yandex-cloud-adapter/issues/68),
[#69](https://github.com/kvazzie/astro-yandex-cloud-adapter/issues/69), and
[#70](https://github.com/kvazzie/astro-yandex-cloud-adapter/issues/70).
Resolve these release blockers and update this section before publishing the
notes. Current local direct-event tests do not prove production direct URL support.
