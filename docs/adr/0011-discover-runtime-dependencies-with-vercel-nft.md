# Discover runtime dependencies with @vercel/nft

Function Artifact preparation discovers the runtime packages and files that the emitted server loads with `@vercel/nft`, the Node file tracer that Astro's Vercel and Netlify adapters use, instead of maintaining its own loader analysis. The adapter keeps exact version selection, npm graph semantics and lockfile generation; the tracer only names what the emitted code imports. We accept the tracer's limits deliberately: a load that static tracing cannot follow is not discovered and is not rejected at build time, so the deployed function fails at runtime with "Cannot find module". The `includeDependencies` option of `dependencyStrategy: "install"` pins such packages explicitly, matching the role of `includeFiles` in the Vercel adapter. The public adapter accepts and applies `includeDependencies` only once its activation in #113 lands; until then the staged option has no effect.

Known undiscovered loads include `process.getBuiltinModule("module").createRequire(…)`, an inline `createRequire(import.meta.url)("pkg")` call, `import()` or `require()` with a computed specifier, files reached only through `require.resolve` or `import.meta.resolve`, loaders selected at runtime between modules or values, and a package that a `#` subpath import reaches only through an `imports` pattern such as `"#lib/*": "pkg/*"` or a fallback array, which the tracer does not resolve. Reports of these patterns are expected behavior: the fix is `includeDependencies`, a fixed `import`, or bundling the package, not a broader analysis in this adapter.

`includeDependencies` only pins missing npm packages. A file the tracer misses, such as a template read through a computed path or a local package export target that uses percent-encoded characters like `./my%20entry.mjs` (nft looks up the literal name), fails with `ENOENT` or an incomplete local archive instead; the remedy is to include that file in the deployed output, or in the local package's npm `files`, and to verify the read from a clean artifact.

We also keep the tracer's default analysis, as those adapters do. With it, nft evaluates recognized native-addon locators while tracing; for `require("node-gyp-build")(__dirname)` it loads the application's installed `node-gyp-build` and calls its `path()` to find the prebuilt binary. Tracing can therefore execute code from an installed runtime dependency during the build, with the build process's environment and credentials, including a server-only dependency that prerendering and plugin loading never ran. We accept this as those adapters do: building an Astro application already runs code from its installed dependencies, so the build environment must trust them, and a project that cannot trust a dependency's installed helper should not build with it. Disabling the evaluation would hide a local package's prebuilt native binary from archive validation, so an archive that omits it would pass.
